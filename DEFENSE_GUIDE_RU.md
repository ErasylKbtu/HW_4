# Homework 4 — объяснение и защита

## 1. Что делает проект

StudyFlow — приложение для учебных задач. Пользователь видит список заданий, выбирает одно и отдельно загружает его подробности. Можно создать запись, изменить её, завершить, вернуть в работу или удалить. Данные сохраняются после обновления страницы.

Приложение показывает реальную асинхронную логику: ответ приходит с задержкой, может завершиться ошибкой и может прийти позже другого ответа. Сервер имитируется в браузере через Promise, setTimeout и localStorage.

В PDF разрешено реализовать аналог предложенного fake API. В этом проекте используется такой аналог. В исходной карточке есть 11 содержательных полей: название, курс, преподаватель, описание, срок, приоритет, статус, оценка времени, заметки, время создания и время изменения.

## 2. Какие файлы открыть преподавателю

1. `src/App.jsx` — состояние списка, загрузка через useEffect и обработка изменений.
2. `src/components/TaskDetails.jsx` — отдельная загрузка подробностей и cleanup.
3. `src/api/fakeApi.js` — Promise, задержка, ошибка, CRUD и localStorage.
4. `src/api/settings.js` — параметры сети.
5. `src/components/TaskForm.jsx` — управляемые поля формы.

## 3. Что такое useState

`useState` хранит данные, от которых зависит интерфейс. Когда вызывается setter, React планирует новый рендер компонента с обновлённым состоянием.

Например:

```jsx
const [selectedId, setSelectedId] = useState(null);
```

`selectedId` — ID выбранного задания. Нажатие на карточку вызывает `setSelectedId(id)`. После этого React отображает панель для новой записи.

Основные состояния в App:

| Состояние | Что хранит |
| --- | --- |
| list | Массив заданий, статус загрузки и текст ошибки |
| selectedId | Текущее выбранное задание |
| reload | Счётчик повторной загрузки списка |
| revision | Версия данных, после изменения которой подробности нужно загрузить снова |
| filter, search | Фильтр статуса и поисковый запрос |
| editor, removing | Открытая форма или подтверждение удаления |
| mutation | Команда изменения: тип, ID, название и новые значения |
| mutationError, notice | Ошибка сохранения и сообщение для пользователя |

## 4. Что такое useEffect

`useEffect` синхронизирует компонент с внешней системой после того, как React применил рендер. Здесь внешняя система — асинхронный API.

Запрос не запускается прямо в теле компонента: тело выполняется при рендерах, и такой подход мог бы создавать лишние запросы. Вместо этого запрос списка запускается в Effect:

```jsx
useEffect(() => {
  // Запрос и обработка результата.
  return () => {
    // Очистка предыдущего запуска.
  };
}, [reload]);
```

Первый запуск загружает список. Кнопка Reload увеличивает `reload`, поэтому Effect выполняется ещё раз.

Сам callback Effect не объявляется `async`: async-функция возвращает Promise, а React ожидает функцию очистки или отсутствие возвращаемого значения. В проекте Promise обрабатывается через `.then()` и `.catch()` внутри Effect.

## 5. Dependencies — массив зависимостей

Зависимости определяют, когда Effect должен повторить синхронизацию. React сравнивает каждое значение с предыдущим через `Object.is`.

| Запись | Поведение |
| --- | --- |
| Без массива | Effect запускается после каждого commit компонента |
| `[]` | Effect связан с монтированием и размонтированием компонента |
| `[reload]` | Повторный запуск при изменении reload |
| `[id, revision, retry]` | Повторная загрузка при смене ID, обновлении данных или повторной попытке |

Нужно перечислять реактивные значения, которые Effect использует. Если забыть зависимость, код может работать со старым значением. В проекте `eslint-plugin-react-hooks` проверяет правила Hooks и полноту зависимостей.

Effect сохранения зависит от `[mutation]`. В объекте команды уже находятся ID и значения, зафиксированные при нажатии. Смена `selectedId` не должна перезапускать сохранение, поэтому выбранный ID не читается внутри этого Effect.

## 6. Cleanup — очистка

Cleanup — функция, которую Effect возвращает. React вызывает её перед повторным запуском этого Effect с изменившимися зависимостями и при размонтировании компонента.

В загрузке подробностей используется:

```jsx
let active = true;
const controller = new AbortController();

// Запрос получает controller.signal.

return () => {
  active = false;
  controller.abort();
};
```

У каждого запуска Effect собственная переменная `active`. После очистки старого запуска она становится false. Даже если старый Promise вернёт ответ, проверка `if (active)` запретит ему обновить состояние.

AbortController дополнительно отменяет запрос. В нашем fake API отмена очищает таймер и отклоняет Promise с `AbortError`. Такая отмена является ожидаемым поведением, поэтому красная ошибка для пользователя не показывается.

Две меры дополняют друг друга: отмена прекращает ненужную работу, а `active` защищает интерфейс даже при API, которое не умеет реально отменять запросы.

## 7. Race condition — гонка запросов

Представим следующий порядок:

1. Пользователь выбирает A. Запрос A занимает 3 секунды.
2. Через мгновение выбирает B. Запрос B занимает 0.5 секунды.
3. Ответ B приходит первым, и интерфейс показывает B.
4. Позже приходит ответ A.

Если без проверки записать A в состояние, пользователь будет видеть подробности A при выбранной карточке B. Это race condition: правильность результата зависит от порядка завершения запросов.

В проекте предыдущий Effect очищается, а его ответ игнорируется. Дополнительно у `TaskDetails` установлен `key={selectedId}`. При смене ID React создаёт новую панель с состоянием загрузки. Старые подробности не показываются в новой панели даже на промежуточном рендере.

Ключ сам по себе не заменяет cleanup. Cleanup также нужен для повторной загрузки того же ID при изменении `revision` или `retry`.

## 8. Stale closure — устаревшее замыкание

Обработчик события видит значения из рендера, в котором он был создан. Пока длится запрос, состояние может измениться, но значения внутри уже запущенного обработчика не становятся автоматически новыми.

Например, мы завершаем A, а затем выбираем B. Ответ завершения A должен изменить A, сохранив текущий выбор B.

В обработчике фиксируется ID:

```jsx
const targetId = task.id;
startMutation({
  type: 'complete',
  id: targetId,
  title: task.title,
  values: { status: 'Completed' },
});
```

В настоящем коде значение статуса также учитывает действие Reopen. Принцип тот же: объект команды создаётся в момент нажатия.

После ответа список обновляется по сохранённому ID. Для edit/complete `selectedId` вообще не меняется. Поэтому завершение A не переключает пользователя обратно с B на A.

Важно: сохранённый ID не является ошибкой замыкания. Здесь это намеренно зафиксированная цель операции. Ошибкой было бы применить ответ к другой записи или вернуть устаревшее состояние целиком.

## 9. Зачем функциональное обновление состояния

```jsx
setSelectedId((current) => current === id ? null : current);
```

Эта запись после удаления очищает выбор только в том случае, если удалённая запись всё ещё выбрана. `current` — актуальное состояние на момент применения обновления.

Так же список обновляется через `setList(current => ...)`. Мы берём текущий список и заменяем только запись с нужным ID. Это безопаснее, чем восстановить весь старый массив из замыкания и потерять более свежие изменения.

## 10. Как устроен fake API

В `fakeApi.js` функция `fakeRequest` создаёт Promise. Она вычисляет случайную задержку между minDelay и maxDelay, затем запускает таймер. Когда время истекает, запрос либо отклоняется с ошибкой, либо выполняет операцию над данными и возвращает результат.

Список возвращает сокращённые записи. Полный запрос `getItem` дополнительно загружает описание, преподавателя, заметки и timestamps. Подробности действительно загружаются отдельно, а не берутся из уже полученного полного списка.

| Метод | Значение |
| --- | --- |
| getItemsList | Read: загрузить список |
| getItem | Read: загрузить полную запись |
| createItem | Create: создать |
| updateItem | Update: изменить поля или статус |
| deleteItem | Delete: удалить |

CRUD — Create, Read, Update, Delete: создание, чтение, изменение и удаление.

## 11. Зачем localStorage находится только в API

Компоненты обращаются к методам API и не знают, где лежат данные. Это соблюдает ограничение задания и отделяет интерфейс от хранения.

`localStorage` хранит строки. Поэтому массив объектов сохраняется через `JSON.stringify`, а при чтении восстанавливается через `JSON.parse`. Ключ проекта — `studyflow-assignments-v1`.

При первом обращении база получает примеры задач. Если пользователь удалил всё и в хранилище находится `[]`, список остаётся пустым. Обновление страницы не создаёт примеры заново.

Данные относятся к текущему браузеру и адресу сайта. Они не являются общей базой для всех пользователей. Для реального общего приложения понадобился бы сервер.

## 12. Как предотвращаются конфликтующие операции

Пока `mutation !== null`, кнопки создания, редактирования, завершения, удаления и Reload отключены. Переключать карточки при завершении можно — это позволяет проверить stale closure.

В API есть дополнительный флаг `writing`. Он отвергает вторую одновременную запись, даже если её попытались вызвать в обход кнопок. Флаг освобождается после успеха, ошибки или отмены.

При ошибке поля формы остаются заполненными. Существующие данные не меняются до успешной записи. После ответа интерфейс показывает подтверждение с названием именно той записи, к которой относилась операция.

В этом симуляторе отмена до выполнения таймера предотвращает запись. У настоящего удалённого сервера отмена клиентского запроса не всегда отменяет уже совершённое сервером изменение — это отдельная задача согласования данных.

## 13. Какие состояния обрабатываются

| Состояние | Что видит пользователь |
| --- | --- |
| Loading | Индикатор загрузки списка или подробностей |
| Error | Понятный текст и Try again |
| Empty database | A fresh start и предложение добавить запись |
| Empty search | No matching assignments |
| Success | Список и подробности либо подтверждение изменения |
| Saving | Сообщение о сохранении и отключённые конфликтующие кнопки |

Ошибки API, ошибки валидации и недоступное хранилище обрабатываются. При удалении сначала показывается подтверждение.

## 14. Почему в разработке Effect может запуститься дважды

В `main.jsx` включён `StrictMode`. В режиме разработки React выполняет дополнительный цикл setup → cleanup → setup для Effects при монтировании. Это помогает обнаружить отсутствие очистки.

В проекте первый запрос отменяется в cleanup, а актуальный выполняется. Убирать StrictMode ради сокрытия повторного запроса не нужно. В production этого дополнительного диагностического цикла нет.

## 15. Сценарий защиты на 3–4 минуты

1. Открой приложение. Скажи, что это планировщик учебных заданий на React с отдельным асинхронным API.
2. Покажи полную карточку: название, курс, описание, срок, приоритет, статус, часы, преподавателя, заметки и даты.
3. Выбери Reliable. Создай запись, отредактируй её и обнови страницу. Покажи, что изменения сохранились.
4. Выбери Slow. Быстро переключи несколько карточек. Дождись ответов: должна остаться только последняя выбранная запись.
5. Загрузи незавершённую A. Нажми Mark as completed и сразу выбери B. После ответа статус меняется у A, а подробности остаются у B.
6. Покажи, что во время сохранения нельзя начать конфликтующую запись.
7. Включи Fail next list и нажми Reload. Покажи ошибку, затем Try again.
8. Открой `TaskDetails.jsx` и объясни зависимости, cleanup, active и AbortController.
9. Открой `App.jsx` и покажи сохранённый ID в команде изменения.

## 16. Короткие ответы на вопросы преподавателя

**Почему нельзя просто вызвать API в теле компонента?**  
Тело выполняется при рендерах. Запросы могли бы запускаться снова без контроля. Effect задаёт жизненный цикл синхронизации.

**Что означает cleanup?**  
Очистку предыдущего запуска Effect перед новым запуском или размонтированием.

**Чем race condition отличается от stale closure?**  
Race condition связана с порядком завершения запросов. Stale closure связана со значениями, захваченными из старого рендера. При одной операции могут возникнуть обе проблемы.

**Почему у Effect сохранения нет selectedId в зависимостях?**  
Он не читает selectedId. Цель уже находится в mutation.id. Смена выбранной карточки не должна перезапускать запись.

**Почему нельзя завершить B, пока сохраняется A?**  
Это конфликтующие записи. Интерфейс и API разрешают одну запись за раз, но просмотр других карточек остаётся доступным.

**Почему описание отсутствует в списке?**  
Список отдаёт summaries. Расширенные данные приходят отдельным запросом подробностей по условию задания.

**Почему данные есть после F5?**  
API сохраняет массив в localStorage и читает его при следующей загрузке.

**Какие Hooks использованы?**  
Только useState и useEffect. Пользовательских Hooks и дополнительных Hooks нет.

**Как работает Reload?**  
Кнопка увеличивает reload. Effect с зависимостью `[reload]` отправляет новый запрос, затем обновляется revision подробностей.

**Как доказывается защита от позднего ответа?**  
Есть ручной сценарий со Slow и браузерный тест, в котором отмена специально игнорируется. Старый ответ всё равно не заменяет актуальную карточку благодаря active.
